# Glon AvP G5j — fixing the Tetris walls

Branch: `glon-avp-g5j`  
Base: `75764233a0d53abc44ca8456c82abbeea0f5298e` (G5i)  
Configuration: native 64K, WSL2, AMD Ryzen 5 7535U, GCC 11.4.0,
`-std=c17 -O2`, SDL2. No VM primitive, frozen-memory, geometry, camera,
player, door or Alien-AI change.

## 1. Root cause

The dominant cause is **non-tileable source wall crops**, amplified by repeated
64×64 tiling, low internal resolution and coarse shading.

Measured edge discontinuity (mean absolute RGB difference between opposite
tile edges; a seamless texture should be near zero):

| Texture | Left/right | Top/bottom |
|---|---:|---:|
| existing `wall_panel` | **160.3** | **382.9** |
| existing `wall_service` | **175.0** | **414.4** |
| existing `pipes` | 161.3 | 264.4 |
| existing `rib` | 73.5 | 249.7 |
| new `panel_v2` | **3.5** | **0.4** |
| new `service_v2` | **0.5** | **7.7** |

The G5d contact-sheet crops are presentation crops, not tileable game assets.
Every 64-texel wrap therefore produces a hard edge. At 320×200, 3× nearest
enlargement and 2-pixel wall rays, those edges form the repeated rectangular
"Tetris" pattern. This is genuine source-artwork/tiling failure, not merely a
filtering artifact.

The UV diagnostic also showed **no hidden gaps between wall strips**. The wall
projection's sampling is continuous within each linedef; material changes at
linedef boundaries are intentional.

Secondary contributors:

- 160 rays at 2 pixels each, so each wall ray is a 2-pixel vertical strip;
- 64×64 textures repeated every 256 world units;
- four discrete distance shading levels;
- nearest-neighbour 3× framebuffer enlargement.

## 2. Resolution and ray-count comparison

Baseline configuration:

- Native framebuffer **320×200**; display window **960×600** (3×).
- Wall rays **160**; **2 horizontal pixels per ray**.
- Texture-space wall U: `(u >> 2) & 63`, i.e. 4 world units per texel and a
  256-unit repeat.
- V: `(y - top) * 64 / (bot - top)`, clamped to 0..63.
- Wall shade levels: 4.

Attempted/considered configurations:

| Configuration | Framebuffer | Rays | Result |
|---|---|---|---|
| A | 320×200 | 160 | **baseline, supported** |
| B | 320×200 | 320 | blocked for the default Glon raycaster: four 80-ray hosted source blocks exceed the remaining loader budget (638 cells originally; 478 in raw-wall mode); no silent ray duplication |
| C | 640×400 | 160 | blocked: Glon hardcodes `screen-w/h`, horizon 100, texrow height 200 and `2*sx-319` projection; 640×400 needs parallel Glon projection/texrow, not a host toggle |
| D | 640×400 | 320 | blocked by both C and B constraints |

A raw-mode compact loop could process more rays without duplicated block source,
but that would change the execution model being compared. It was not substituted
silently. No 320-ray or 640×400 image is presented as a real configuration.

The contact sheet labels B/C/D as blocked.

## 3. UV findings

The enhanced diagnostic (`--checker`) uses a high-contrast UV grid with major
and minor lines, colour-coded cells and a gradient. It demonstrates:

- continuous U within each wall;
- correct V mapping from wall top to bottom;
- expected perspective compression, not incorrect stretching;
- texture repeat boundaries are periodic and intentional;
- no missing wall-strip geometry/gaps.

The actual defect is at the 64-texel wrap: old crops do not match their own
opposite edges. New textures pass edge-continuity checks.

## 4. Original versus improved texture

Two original seamless 64×64 industrial textures were generated by
`tools/gen_g5j_textures.py`:

- `sprites/textures_g5j/panel_v2.png` — inset plate, seams, rivets, vent,
  restrained blue/grey palette;
- `sprites/textures_g5j/service_v2.png` — ribbed service wall, pipe bands,
  fasteners, amber indicator.

They are individual game assets, not contact-sheet crops, with no labels or
borders. Material mapping under `--new-textures`:
material 0/2/4 → panel_v2; material 1/3 → service_v2; door remains the existing
door material.

Visual result: the repeated hard-edged blocks disappear; walls read as
continuous panels with intentional seams. The new assets add 32,768 bytes of
compiled texture memory (16,384 each) and remain in native host memory.

Performance trade-off: five runs with new textures measured a median
**19.6 FPS** (range 16.3–28.9 including a first-run timing outlier), wall
17.73 ms, texrow 22.84 ms, total 51.84 ms. This is a modest cost increase over
the 21.7 FPS baseline; it remains above the 15 FPS target. Texture sampling cost
is unchanged; the extra texture working set/cache pressure is the likely cause.

## 5. Shading comparison

Existing wall shading uses four discrete levels derived from Glon's distance
(`48/64/82/100%` brightness).

`--smooth-shading` keeps the level endpoints but interpolates brightness from
the current wall span height, which is inversely related to distance. This is a
host-side colour application; Glon's `shade` output and S1/HOST counts are
unchanged.

Smooth runs: median **21.4 FPS**, wall 16.23 ms, texrow 20.50 ms, total
46.63 ms. New textures + smooth: median **21.6 FPS**, wall 16.11 ms, texrow
20.44 ms, total 46.30 ms.

Visually, smooth shading removes some horizontal banding, but the tile-edge
seam fix is the major improvement. Floor/ceiling shading remains the existing
four-level scheme; no lighting engine was added.

## 10. Recommended production configuration

Keep configuration A (**320×200, 160 rays**) and preserve the G5h prepared-wall
execution. Adopt the two seamless G5j textures as the production wall-art
direction, optionally with smooth wall shading. Do not adopt bilinear output
blur as a substitute for fixing tiling.

The visual improvement comes from eliminating non-tileable 64×64 source crops,
not from adding pixels. A 640×400/320-ray renderer is a separate G5k/G5j follow-up
requiring Glon projection/texrow redesign and loader-budget work; it is not
justified by this experiment because the principal defect was source texture
tiling.
