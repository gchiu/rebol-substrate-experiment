- state-var: executed LIT addr @ / LIT addr ! pairs in [RV_BASE, GC_HEAP_BASE),
  counted as two instructions each.
- macro exec: CALL/EXIT/BRANCH/>R/R>/R@/SWAP cells as a share of executed
  instructions. It is conservative for masm CALL label (emit_call_fwd), whose
  internal >R is counted but whose whole expansion is not labelled CALL.
- scan: mark_closure_inline plus scan_closures as a share of execution.

FIBONACCI, NAIVE RECURSION, n = 18 (8,361 activations)

Glon:
  definition: fib: func [n] [ either < n 2 [ n ] [ + fib - n 1 fib - n 2 ] ]
  total executed: 30,914,744
  per activation: 3,697 (total / 8,361; one top-level invocation included)

masm, same algorithm, untagged integers inside and tagged at the boundary:
  fibm: masm 1 [ LIT 16 DIV CALL F LIT 16 MUL ARITY 1 EXIT
    F: DUP LIT 2 LT ZBRANCH R EXIT
    R: DUP LIT 1 SUB CALL F >R LIT 2 SUB CALL F R> ADD EXIT ]
  total executed: 334,942 (trace) / 336,617 (dump; the dump has slightly more
                  setup)
  top-level Glon + fibm wrapper overhead: 527
  per F activation: (334,942 - 527) / 8,361 = 40.0

  Macros per F activation [D]: about 33 instructions (CALL expansions,
  including their internal >R, EXIT, explicit >R, R>). Primitive dispatches
  would be about 3 per activation (one CALL, one EXIT, one >R, one R> across
  the tree; 8,362 CALL + 8,362 EXIT + 4,180 >R + 4,180 R> over 8,361
  activations). A five-primitive extension therefore gives about
  40 - 33 + 3 = 10 instructions per activation [D], not a direct measurement.

GC AND THE CONSERVATIVE SCAN

GC is 27.5% of runtime code and 25.8-93.0% of execution in the GC-bearing
workloads. mark_closure_inline alone is 16.9% (deflate), 41.9% (latex),
43.7% (mem) and 29.0% (binary) of executed instructions; adding the
scan_closures walk gives 34.0% for binary. The scan walks object sizes from
the heap base per candidate because the return stack holds data and integer
tags are x16.
