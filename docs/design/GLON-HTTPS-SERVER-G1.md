# Glon HTTPS Server — G1: Standalone G1 HTTPS Server

**Status:** implemented, locally committed, not pushed or deployed.  
**Branch:** `experiment/glon-https-g1`  
**Base commit:** `935e9f7584748fb80590660985bba0af851a03fa`  
**Frozen S1:** `f90496c26dc45c7a387d8fc8639cd2781507d3d2` (verified unchanged)

This milestone serves a single HTML page generated by Glon over HTTPS from one
native executable. CivetWeb owns TCP/TLS/HTTP; Glon owns the handler and the
response bytes. No Apache, Nginx, Node.js, Python or other language runtime is
needed at run time.

---

## 1. Networking library decision

### Selected: CivetWeb 1.16

| Criterion | CivetWeb 1.16 |
|---|---|
| Licence | MIT (`third_party/civetweb/LICENSE.md`) |
| HTTP | HTTP/1.1 request parsing, limits, keep-alive, connection cleanup |
| TLS | OpenSSL 3 transport; no cryptography written here |
| Event model | Internal master/worker thread loop; one worker configured for Glon |
| Linux | POSIX sockets/pthreads, proven target |
| Embedding | Single `civetweb.c` plus small `.inl` fragments |
| Dependencies | OpenSSL 3 development files at build time; `libssl.so.3`/`libcrypto.so.3` at run time |
| Size overhead | +152 KiB stripped over the minimal CLI (CivetWeb only; OpenSSL is dynamic) |
| Maintenance | Long-running MIT project; 1.16 is the latest published release (2023-04-10) |

The sources are vendored unmodified in `third_party/civetweb/` with a provenance
note. The build disables CGI, caching and dynamic OpenSSL loading
(`-DNO_CGI -DNO_CACHING -DNO_SSL_DL`). TLS failure is therefore fail-closed.

### Considered and rejected

- **Mongoose.** Small and capable, but dual-licensed GPLv2/commercial. A GPLv2
  combined binary would impose GPL obligations on the whole distribution; the
  commercial option is not appropriate for this milestone. Its built-in TLS
  would also add a larger in-tree cryptographic surface than reusing OpenSSL.
- **GNU libmicrohttpd.** A solid LGPL-2.1+ option with TLS through GnuTLS or
  OpenSSL, but it adds LGPL relinking/distribution considerations and does not
  offer a smaller integration than CivetWeb for this single-listener use.

No HTTP parser, TLS implementation or cryptography was written for this
milestone. CivetWeb also supplies bounded request-size handling, timeouts and
connection cleanup.

## 2. Reused Glon infrastructure

The HTTP module is deliberately built like the existing optional file module,
not as a second host architecture.

| Existing facility | Reuse |
|---|---|
| Persistent session facade (`r0_s1_session_run_block`) | One runtime, all libraries and the application loaded once; requests run in that same session |
| Optional module convention (`make glon MODULES=...`) | `MODULES=http`, `MODULES=file,http`; the minimal build links nothing from the module |
| Host request/reply pattern (`modules/file.glon`, `glon.c`) | Host builds a transient source expression; Glon returns structured values; loader-heap high-water is restored after each turn |
| `mk-string` byte-string construction | Request method/path and response bytes cross as ordinary managed strings; no native pointers cross the boundary |
| `SIN!`, `raise`, `judge`, `create-sin` | Handler failures and stale handles use the existing error system; no parallel error type |
| Persistent-session conventions | Definitions and the handler closure persist; only the per-request blocks are transient |
| Existing build/CI conventions | Makefile selection, staged `glon-lib/`, `check-frozen-s1.sh` |

`GLON_LIVE`'s request-fragment/raw-byte idea was reviewed. Its dispatch
(`route`/`do-event`) is experimental and would add a second application-event
vocabulary. The file module's direct session-turn pattern is simpler for a
native server and is the model used here.

Frozen S1, the parser, the evaluator, the GC, the scheduler and the HOST
service table are unchanged.

## 3. Architecture and data flow

```text
client
  |
  | TLS + HTTP/1.1
  v
CivetWeb  (listen, TLS, parse, request limits, timeout, close)
  |
  | begin_request(conn)
  v
glon_http.c  (opaque integer request id; no native pointers)
  |
  | source turn:  [ http/dispatch <id> <method-string> <path-string> ]
  v
persistent Glon session
  |
  | http/dispatch -> handler closure -> application code
  |                -> http/respond request status type body
  v
http/response = [id status content-type body]   (global, rooted)
  |
  | source turn:  [ http/take-response ]
  v
glon_http.c  (validate id == active id; copy into bounded host buffer)
  |
  | status, headers, body bytes
  v
CivetWeb  -> client
```

### Responsibilities

- **CivetWeb:** listening sockets, TLS negotiation, HTTP parsing, protocol
  limits, connection lifetime and cleanup.
- **C bridge (`glon_http.c`):** numeric request ids, bounded source-expression
  construction, response extraction and id validation, transport writes,
  counters, signal shutdown.
- **Glon (`modules/http.glon`):** listener vocabulary, handler storage,
  dispatch, response queue, stale-handle check, `SIN!` handling, application
  stop flag.
- **Application (`examples/https-g1/server.glon`):** routing/body decisions.
  The HTML is not in C.

### Request handle lifetime

A request is represented in Glon as an opaque block `[id method path]`. The id
is a monotonically increasing integer, never a pointer. `http/respond` accepts
a response only when the request block's id equals the id currently being
dispatched. The C bridge repeats the id check before writing. A stale or
fabricated handle therefore cannot address another connection. The stale-handle
test in §7 exercises this.

### Execution and ownership model

- One Glon runtime, one CivetWeb worker thread (`num_threads=1`).
- The main thread loads the application, then hands the session to the one
  worker for the lifetime of the listener. The main thread only polls atomic
  shutdown/counter state.
- The Glon evaluator is never entered from two threads at once. A mutex protects
  the dispatch/response sequence as defence in depth.
- Network concurrency is not Glon task concurrency. Multiple TCP/TLS clients may
  be connected and queued, but request handlers are executed one at a time.
  M1 scheduling is not used or redesigned.
- Keep-alive is disabled. Each response sends `Connection: close`.

### Completion and error propagation (honest description)

There is **no asynchronous Glon continuation** in G1. CivetWeb's callback calls
`http/dispatch`; when that source turn returns, the host immediately calls
`http/take-response` and writes the response. The handler cannot return a value
and complete later. Network waiting happens inside CivetWeb before and after the
turn, not inside Glon evaluation.

- A handler `SIN!` is caught by `judge` inside `http/dispatch`. If the handler
  did not queue a response, a 500 `internal error` response is generated and
  the server continues.
- A handler that completes without calling `http/respond` gets a 500
  `no response`.
- A handler returning a `SIN!` value (rather than raising it) is treated as a
  failure, because G1 cannot distinguish a returned SIN! from a caught one.
- A machine-level fail-stop (for example return-stack or managed-heap
  exhaustion) is not a `SIN!` and cannot be judged. The host sends a 500, marks
  the listener fatal and stops it rather than continuing with a possibly
  inconsistent runtime.
- `http/respond` raises `SIN! 'http 'stale-request` for an old request id and
  `SIN! 'http 'no-request` outside a dispatch.
- Startup TLS failure is a hard failure. The application configured a listener,
  so the host does not fall back to plain HTTP or silently exit.

## 4. Glon application and vocabulary

### Application source

`examples/https-g1/server.glon`:

```glon
;; examples/https-g1/server.glon -- G1: one HTML page served by Glon over HTTPS.
;;
;; The native host supplies sockets, TLS and HTTP parsing (optional http
;; module).  This file is the whole application: a handler closure and a
;; listener request.  Editing this file changes the response without
;; recompiling the native executable.
[
home: func [request] [
    http/respond request 200 "text/html; charset=utf-8"
        "<h1>Served by Glon</h1>"
]

http/listen 8443 :home
]
```

### Vocabulary (`modules/http.glon`)

| Word | Purpose |
|---|---|
| `http/listen port handler` | Register the listening port and handler closure |
| `http/respond request status content-type body` | Queue the response for the active request |
| `http/stop` | Ask the host to stop after the current response |
| `http/dispatch` | Host-only entry; stores the request and calls the handler inside `judge` |
| `http/take-listen` | Host-only; returns `[1 port]` or `none` once |
| `http/take-response` | Host-only; returns `[id status type body]` or `none` |
| `http/stopped?` | Host-only; reports the application stop flag |

`http/listen 8443 :home` is evaluated while the source file is loaded. The host
starts the listener only after every source file has loaded, and only if
`http/take-listen` returns a configuration.

## 5. Build and launch

### Dependencies

Linux build:

```sh
sudo apt-get install build-essential libssl-dev
```

The optional module is the only part that needs OpenSSL headers. The minimal
CLI has no TLS dependency.

If the development package is unpacked into a private directory (for example on
a machine without root), point the build at it without editing the Makefile:

```sh
make glon MODULES=http \
  OPENSSL_CFLAGS="-I/path/to/usr/include -I/path/to/usr/include/x86_64-linux-gnu" \
  OPENSSL_LIBS="-L/path/to/usr/lib/x86_64-linux-gnu -lssl -lcrypto"
```

### Build

```sh
make glon                 # minimal CLI, no HTTP
make glon MODULES=file    # existing optional file module
make glon MODULES=http    # this milestone
make glon MODULES=file,http
```

The selected configuration is tracked in `.glon-config`, so switching module
sets relinks. Unknown module names fail at build time.

### Generate a local test certificate

```sh
tests/https-g1/make-cert.sh
```

This creates `tests/https-g1/.cert/server.pem` (certificate plus private key,
combined as CivetWeb expects) for `localhost`/`127.0.0.1`, valid for two days.
The directory is git-ignored.

### Launch

```sh
./glon --http-cert tests/https-g1/.cert/server.pem \
       examples/https-g1/server.glon
```

It listens on `https://127.0.0.1:8443`. Useful options:

| Option | Meaning |
|---|---|
| `--http-cert FILE` | Combined PEM certificate + private key (required if listening) |
| `--http-bind ADDR` | Listening address, default `127.0.0.1` |
| `--http-max-requests N` | Stop after N completed responses (bounded tests) |
| `--http-timeout-ms N` | Per-connection idle timeout, default 10000 |
| `--http-max-request-size N` | CivetWeb request-size bound, default 8192 |
| `--http-report` | Print request and managed-heap counters at shutdown |

### Test with curl

```sh
curl -k https://127.0.0.1:8443/
```

Expected:

```text
<h1>Served by Glon</h1>
```

### Acceptance suite

```sh
make https-g1-test
```

This builds the minimal, file, HTTP and combined configurations, checks the
minimal smoke test, generates the certificate and runs the bounded HTTPS suite
twice (HTTP and file+http).

The suite can also be run directly:

```sh
python3 tests/https-g1/acceptance.py --glon ./glon
```

(`GC_HEAP_BASE` is 32,768, so this is 7,232 cells of address space reached). It
is not an unbounded-growth measurement; live cells after collection stay at the
small persistent set.

## 8. Limitations and security boundaries

### Scope not implemented

- General routing frameworks/static file serving/databases
- WebSockets, authentication, sessions, template engines
- Automatic certificate provisioning, HTTP/2 or HTTP/3
- Request-body API (a body larger than 64 KiB is rejected; smaller bodies are
  not exposed to Glon in G1)
- Public-internet hardening

### Concurrency

- One CivetWeb worker. HTTP requests are serialized through the one Glon
  evaluator. Multiple clients may connect and overlap at the network layer, but
  their handlers do not run concurrently.
- A slow client can delay later clients. This is deliberate backpressure, not a
  scheduler feature. Per-connection timeouts bound the wait.
- `num_threads` must not be raised without an explicit evaluator-ownership
  design. Doing so would enter the same Glon runtime concurrently.
- No M1 tasks are used. Network concurrency is not Glon task concurrency.

### Protocol and application bounds

- `max_request_size` defaults to 8,192 bytes. Larger requests are rejected by
  CivetWeb before or during dispatch.
- A Glon response body is capped at 64 KiB by the bridge.
- The request URI is capped at 2,048 bytes and the method at 32 bytes before
  Glon dispatch.
- Keep-alive is disabled; each response closes the connection.
- Only the method, decoded local path and numeric id are exposed to the handler.
  Headers, query-string helpers and request bodies are not part of the G1
  vocabulary.

### TLS

- Certificates and keys are combined in the PEM file named by `--http-cert`.
  CivetWeb/OpenSSL validate the file during startup. Startup fails if it cannot
  initialise TLS.
- There is no plaintext fallback, no certificate hot reload, no client-certificate
  authentication, no OCSP/CRL handling and no automatic renewal.
- The private key is a local file; file permissions are the operator's
  responsibility (the test script uses mode 600).
- OpenSSL security updates are part of the deployment's system maintenance.

### Trust

- The Glon application is trusted code. There is no sandbox around the handler
  beyond the existing language and memory model.
- The app cannot choose the certificate path or bind address; those are host CLI
  decisions. The app chooses only whether to listen, the port, and the response.
- No filesystem mapping happens for HTTP paths. There is no path traversal
  surface in this milestone because no path is turned into a file operation.

### Combination with the file module

`MODULES=file,http` builds and passes the HTTPS suite. However, G1 does **not**
drain the asynchronous file-I/O request queue from inside an HTTP handler. Using
`file/read` or `file/write` asynchronously inside an HTTP handler is therefore
not supported in this milestone and should be treated as a follow-up integration
task. A file+I/O app should not assume the two event loops are merged.

## 9. Remaining work for a DigitalOcean deployment

G1 is a working local HTTPS page, not a production deployment. A small VPS run
would still need:

1. A supported Linux target and `build-essential`, `libssl-dev`; build with
   `make glon MODULES=http`.
2. A real certificate (for example Let's Encrypt) and a renewal strategy.
   Automatic provisioning is out of scope; certificate reload currently means
   restarting the process.
3. Explicit binding (`--http-bind 0.0.0.0` or a private interface), firewall /
   cloud security-group rules, and a non-root service user.
4. A systemd unit (or equivalent) with restart policy, working directory,
   certificate/key permissions, resource limits and log collection.
5. Operational limits: connection/rate limiting, request logging, monitoring,
   and policy for the single-worker serialization.
6. A decision on request bodies, routing and static assets if the application
   grows beyond one generated page.
7. Security updates for OpenSSL and periodic review of the vendored CivetWeb
   version.
8. If the app needs asynchronous or concurrent work, a separate approved design
   for evaluator ownership/tasking; G1 deliberately does not change M1.
