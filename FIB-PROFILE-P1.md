# FIB-PROFILE-P1.md — profiling naïve recursive Fibonacci

Phase P1 of the Fibonacci experiment: discover where Glon spends its *abstract
work* when evaluating naïve recursive `fib`. **No optimisation is performed
here.** S1 remains frozen (verified before and after).

Two questions are answered separately:

1. **TRACE** — what actually happens while evaluating `fib` (Part A).
2. **PROFILE** — where the evaluator/runtime spends its work (Part B), and a
   clearly-separated wall-clock measurement (Part C).

---

## 1. Exact benchmark source

```glon
fib: func [n] [
    either <= n 1 [
        n
    ][
        + fib - n 1 fib - n 2
    ]
]
```

Run as `[ fib: func [n] [ either <= n 1 [ n ] [ + fib - n 1 fib - n 2 ] ] fib N ]`.
No memoisation, no iterative rewrite, no special Fibonacci native, no
benchmark-specific evaluator optimisation.

**Instrumentation is compiled only under `-DR0_S1_PROFILE`.** The baseline
build emits zero added code; the profile build adds a small block of counter
cells (in the free region `24655..24674`) and per-event increments in
`r0_s1_runtime.c` (above the frozen substrate). The frozen files
`s1.c`/`s1.h`/`tests.c`/`adversarial.c`/`claims.c` are untouched.

## 2. Part A — small human-readable trace (fib 5)

Machine-generated by a gated trace hook (three events, printed as
`E`/`R`/`B` + one number each). The hook is compiled under `-DR0_S1_PROFILE`
and enabled at runtime by `PF_TRACE`; it changes no semantics.

Event encoding (documented here so the raw lines are auditable):

- `E <d*100 + n>` — closure entry at recursion depth `d` with argument `n`.
- `B <0|1>` — the base-case decision, i.e. the result of `<= n 1`.
- `R <result>` — closure exit with that result.

Raw event stream (fib 5):

```
E105  B0    fib(5),  n=5,  5<=1? no
  E204  B0    fib(4),  n=4,  no
    E303  B0    fib(3),  n=3,  no
      E402  B0    fib(2),  n=2,  no
        E501  B1  R1      fib(1) base -> 1
        E500  B1  R0      fib(0) base -> 0
        R1                fib(2) -> 1+0 = 1
      E401  B1  R1        fib(1) base -> 1
      R2                  fib(3) -> 1+1 = 2
    E302  B0              fib(2),  n=2,  no
      E401  B1  R1        fib(1) -> 1
      E400  B1  R0        fib(0) -> 0
      R1                  fib(2) -> 1
    R3                    fib(4) -> 2+1 = 3
  E203  B0                fib(3),  n=3,  no
    E302  B0              fib(2),  n=2,  no
      E401  B1  R1        fib(1) -> 1
      E400  B1  R0        fib(0) -> 0
      R1                  fib(2) -> 1
    E301  B1  R1          fib(1) -> 1
    R2                    fib(3) -> 2
  R5                      fib(5) -> 3+2 = 5
```

Decoded as a tree (15 activations = `2*F(6) - 1`, 8 base cases = `F(6)`):

```
fib(5)
├─ fib(4)
│  ├─ fib(3)
│  │  ├─ fib(2)
│  │  │  ├─ fib(1) → 1
│  │  │  └─ fib(0) → 0
│  │  │  → 1
│  │  └─ fib(1) → 1
│  │  → 2
│  └─ fib(2)
│     ├─ fib(1) → 1
│     └─ fib(0) → 0
│     → 1
│  → 3
└─ fib(3)
   ├─ fib(2)
   │  ├─ fib(1) → 1
   │  └─ fib(0) → 0
   │  → 1
   └─ fib(1) → 1
   → 2
→ 5
```

This confirms the expected high-level path: each `fib(n)` with `n>1` evaluates
`<= n 1` (false), recurses on `n-1` then `n-2`, and adds; each `n<=1` returns
`n` directly. The result (`5`) and activation count (15) match the closed-form
check in §3.

## 5. Lookup costs (Part B focus)

We measure both the *frequency* of lookups and the *cost per lookup*:

- **Lookups are frequent**: 7.0 per activation (`1 699 493` for fib 25), because
  `either`, `<=`, `+`, `-`, `fib`, `n` are each re-resolved on every evaluation.
- **Each lookup is a linear search**, not a hash: 6.86 binding slots examined per
  lookup, plus 0.64 parent hops per lookup.

The pattern is uniform: the freshly created child context holds only the
parameter `n` (1 slot). Every global word (`either`, `<=`, `+`, `-`, `fib`) is
missed in the child (1 slot scanned) and then found by a **linear walk of the
global context** (which has 14 entries after `fib` is defined) — e.g. `either`
costs ~11 slots + 1 parent hop, `fib` ~13 slots + 1 hop. `n` costs 1 slot and 0
hops.

So the answer to "frequent vs expensive" is **both**: the same handful of words
are looked up millions of times, and each lookup is a linear chain walk whose
cost grows with the size of the global context.

## 6. Allocation / GC costs (Part B focus)

**Recursive function calls allocate.** Every `fib` activation heap-allocates two
managed objects:

- a child lexical context (64 cells: 16-byte header + 48-byte payload), and
- an activation frame (32 cells: 16-byte header + 16-byte payload),

= **96 cells per activation**. The parameter binding (`n`) and the frame
(non-local `return` bookkeeping) are both heap objects, even though neither
escapes the activation.

The managed heap is a fixed `[32768, 40000)` = 7 232 cells. Because each
activation allocates 96 transient cells, the heap fills and forces a
stop-the-world mark/sweep roughly every ~58 activations:

| n | allocations | collections | allocs per collection | cells per collection |
|---|---|---|---|---|
| 10 | 355 | 2 | 177 | 8 512 |
| 15 | 3 947 | 29 | 136 | 6 532 |
| 20 | 43 783 | 353 | 124 | 5 953 |
| 25 | 485 571 | 4 164 | 117 | 5 598 |

The heap high-water hits the ceiling (`40000`) in every run, and each
collection reclaims ~5 760–6 528 free cells (almost the whole heap): the
overwhelming majority of allocations are dead frames/contexts of *completed*
recursive calls, reclaimed the moment they fall off the call stack. GC
collections grow in direct proportion to activations (2, 29, 353, 4 164 —
the same ~11× per +5 `n` as the call count).

## 7. SP / RP depth (Part B focus)

Measured at closure entry (min values recorded per run):

| n | max depth | RP high-water (cells below `RS_INIT`) | SP high-water (cells below `DS_INIT`) |
|---|---|---|---|
| 10 | 10 | 120 | 6 |
| 15 | 15 | 185 | 8 |
| 20 | 20 | 250 | 11 |
| 25 | 25 | 315 | 13 |

- Recursion depth equals `n` (the longest chain `fib(n) → fib(n-1) → … → fib(1)`).
- Return-stack depth ≈ **12.6 cells per recursion level** — each closure
  invocation pushes several continuations and saves `RV_ARITY`/`RV_CLOSURE` etc.
- Data-stack depth is shallow (≤13 cells) because values are produced and
  consumed immediately; the work is on the return stack and the heap, not the
  data stack.

## 8. Part C — wall-clock (separate)

**Method.** Monotonic `CLOCK_MONOTONIC` around `r0_s1_run` only. The program
`[fib-def fib n]` is parsed once (parsing excluded), warm-up run first, then K
repeated runs, median reported. The definition (one closure allocation + one
binding) is a fixed sub-1% constant and is included; it is negligible for
`n ≥ 15`.

**Build.** `fib-timing` (baseline, no `-DR0_S1_PROFILE`) is the authoritative
timing. The instrumented build is measurably slower (counters): fib 10 median
0.0177 s vs 0.0156 s baseline (≈ +13% from the counter increments). These
instrumented numbers are **not** claimed to represent normal Glon speed.

Results (CURRENT NATIVE/HOST BUILD, Linux x86-64, `-O0`):

| n | reps | median | min | max |
|---|---|---|---|---|
| 10 | 100 | 0.015618 s | 0.013890 s | 0.058562 s |
| 15 | 50 | 0.187048 s | 0.171696 s | 0.246901 s |
| 20 | 20 | 2.208087 s | 2.015944 s | 2.657841 s |
| 25 | 5 | 24.716710 s | 23.470447 s | 26.993159 s |

Each +5 in `n` multiplies time by ~11–12× (matching the exponential growth of
`calls(n)`), with no measurable sub- or super-exponential drift — i.e. the
constant per-activation cost is stable across `n`.

## 9. Top three apparent sources of overhead

Ranked by measured abstract work per `fib` activation:

1. **Per-call heap allocation + GC churn.** Two heap objects (96 cells) per
   activation, filling the 7 232-cell heap every ~58 activations and forcing a
   full mark/sweep each time. `fib 25` = 485 571 allocations and 4 164
   collections to compute one integer. This is the largest and most avoidable
   cost: neither the child context nor the activation frame needs to be a
   managed heap object for a non-escaping call.

2. **Symbol lookup is a repeated linear chain walk.** 7 lookups per activation,
   each scanning ~7 binding slots (parameter slot then a linear walk of the
   global context). `fib 25` performs 1.7M lookups examining 11.7M slots to
   resolve the same six words over and over. The search cost is O(context size)
   per lookup and grows with the global context.

3. **Evaluator dispatch overhead.** ~11 subexpression tag-dispatches and 2
   block-evaluator iterations per activation, vs. only ~3.5 actual native
   operations of real arithmetic. The evaluator spends most of its time
   walking, tagging/untagging, reducing, and discarding — not adding.

Supporting (secondary): `either` performs its truthiness check as two HOST ops
and evaluates all three branches' source forms before selecting one, and every
arithmetic native pays the 2-arg reduce/discard round-trip.

## 10. Things NOT measured

- **Dynamic S1 primitive counts** (LIT/DUP/DROP/@/!/0BRANCH/HOST/HALT) are
  **unavailable without perturbing frozen `s1_run`**, and `s1_run` was not
  modified. All counts here are at the R0/runtime level, emitted above S1.
- **HOST calls broken down per service** beyond arithmetic natives: `RV_HOSTCALLS`
  counts only the arithmetic/comparison natives (441 … 606 961). The HOST ops
  inside `lookup`/`set`/`either`-truthiness/GC/alloc are **not** individually
  counted (that would require instrumenting every `asm_host` site); the
  `either` truthiness check alone adds an uncounted ~2 HOST ops per activation.
- **S1 instruction-level hot spots** (which opcode, which instruction) — out of
  scope without touching frozen S1.
- **fib 30** (and any `n > 25`): impractical on this host (≈11× fib 25).
- **Cache/perf events, memory bandwidth, or any wall-clock beyond the single
  host build** — not collected; the numbers are explicitly native-build only.

## 11. Proposed optimisations (NOT IMPLEMENTED)

Recorded for the next phase; none is applied in P1:

1. **Stack-allocate the activation frame and child context.** A non-escaping
   call's frame/context do not need to live in the managed heap; moving them to
   the return/data stack (or reusing pooled objects) would eliminate the 96
   cells/activation and almost all GC churn — the single largest win.

2. **Reduce lookup cost.** Cache the resolved binding in the closure/site (a
   per-body constant pool), or jump-thread word→binding, so repeated `either`/
   `<=`/`+`/`-`/`fib` lookups do not each re-walk the linear context chain.

3. **Superinstruction / fused dispatch.** Fuse the common
   `word-lookup → native-dispatch → 2-arg reduce` sequence (and the `either` +
   `<=` pair) to cut the ~11 subexpression dispatches and the reduce/discard
   round-trips per activation.

4. **(Out of scope here)** Algorithmic memoisation/iteration would change the
   benchmark and is explicitly prohibited by the brief; it is noted only as the
   obvious asymptotic fix.
